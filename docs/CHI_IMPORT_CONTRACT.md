# CHI import contracts and C1 audit

Baseline: `0f1956d`, 2026-10-23. The C1/C2 contracts below are retained; the
C3 extension is specified in the final section. See the
[campaign plan](CHI_EDITABLE_CAMPAIGNS_PLAN.md). The original executable/data remain
the behavioral authority; these contracts preserve the current port baseline.

## Inventory and capacities

**VERIFIED structural inventory:** [machine-readable report](chi-import-inventory.json),
generated by `python3 tools/chi_audit.py`. It contains fingerprints and numeric
metadata, never decoded text/pixels. There are 77 supported inputs: the executable
for extraction and 76 runtime resource files. Verification/demo files and
original personal saves are not imported.

There are 26 BLD programs and 1,816 statically reachable instructions; every
native action 1–47 occurs in at least one program. The report records each
action's exact script contexts, menus and referenced story indices. HUT is the
largest payload, 8,499 bytes, inside the 9,000-byte interpreter limit. Static
traversal does not establish branch execution coverage.

The 14 local MTPs fit 64×64; MAP15 is the separate raw 32×24 map room. The maximum
populated entrance count is 12 of 16 slots. No C2 limit expansion is needed.
Do not combine original instructions with the 1,024-node authored event pool or
map the 100-byte legacy state onto the 64 authored flags. Native service/building
kinds (26) are not the authored shop collection (16).

The current native capability report measures resources at 3,219,408 bytes,
project at 29,213,624, state at 16,848 and encoded state at 20,480. These are
baseline build measurements, not portable ABI promises. Allocate project/resource
loads on the heap. New resource staging must not put another project on the
Windows stack. Full generic authored-world conversion is deferred to C3; retain
the exact original generator in C2.

## C2 runtime package contract

Keep `btp-project-v1`/schema 1 and add an explicit optional extension, rejected by
older runtimes: `startup: chi-import-v1`, `requires: chi-local-dos-1.03`,
`campaign: campaign.json`, and ordered `resources` paths. Other startup/dependency
combinations retain their existing interpretation and cannot use this extension.
Advertise `btp-chi-campaign-v1` in runtime capabilities. The extension is opt-in;
the legacy required fields and save envelope stay unchanged.

`resources` must name exactly the 76 canonical `chi/<original filename>` inputs
followed by `chi/talk-data.bin`, `chi/combat-data.bin`, `chi/world-data.bin`.
Validate the exact set/order, child paths, regular files, case, sizes and total
budget. Hash each file into the project digest. Never include BTECH.EXE, GAME
saves or arbitrary files. The resource loader consumes only this validated set.
It must bind the save fingerprint to the same bytes actually decoded, not a
second read which could observe a different edit.

`campaign.json` has format `btp-chi-campaign-v1`, schema 1, explicit `edition`
(`original` or `updated`) and `dialogue_overrides`: zero to 373 objects with
unique `index` (0–372) and `text` (maximum 512 bytes, original supported character
set). The final rebuilt dialogue must fit the existing 16,384-byte budget.
No other fields are accepted. Missing/duplicate/unknown fields fail validation.
This is the C2 editable slice; full BLD and mission content remains C4.

Original has broker/Enhanced capabilities off; Updated has them on, independently
of exported roster size. Existing authored packages keep their prior behavior.
Imported Original may use a definitions container, but its compatibility combat
templates/prices/weapon IDs must not be taken from normalized library presets.
Updated export must round-trip current records and custom weapon mapping.

The manifest and every executable dependency participate in strict project
identity. Absolute source/destination paths and import timestamps are not included
in gameplay content. New imports receive independent IDs; repeated builds of an
existing project preserve IDs. Six-slot paths use the established project suffix.
Existing normal-game saves remain untouched, with no implicit conversion.

The editor includes the campaign file and resources in ordinary snapshots,
validation, conflicts, Undo and source builds. The campaign JSON is a runtime
file, even if the initial editor implementation stores its editable bytes in the
document's auxiliary-file collection. It participates in every runtime digest.

## Import transaction and provenance contract

Check all 77 source fingerprints against the audited corpus before extraction.
Read only regular files and preserve originals. Use a sibling private staging
parent; generate both profiles inside it and validate before publishing the new
parent atomically. Occupied/symlink destinations are errors. Recheck all source
fingerprints before publication. Cancellation, errors and races never overwrite
a finished project. Resume is not promised in C2; retry starts a new transaction
and discards only its own private staging. Completed imports need no shared
mutable cache or original executable: each owns all 79 runtime resource files.

Local `IMPORT.json` records input hashes, extractor/schema versions, profiles,
generated file hashes and editability dispositions. Treat the entire imported
campaign (including raw copies, converted caches, native text overrides and
future edited/cloned derivatives) as local original-derived content for export.
This conservative boundary must survive metadata editing/removal: the runtime
manifest's imported dependency is itself a provenance signal.

Last Beacon's 20 known derived images need a metadata-only reconstruction recipe
and synthetic placeholders in redistributable data. **Further C2 inspection found
17 already contain custom pixel edits:** their public recipes restore the recorded
original base, while the exact private derivatives stay in the owner's working
files and an ignored backup. These recipes do not reproduce those custom edits.
Preserve the owner's three
dirty working files byte-for-byte; use HEAD as the source when preparing a clean
tracked baseline. Reconstruction into a new private project applies only the
recipe's declared images using the native tile atlas, leaving authored images
and user projects untouched. New edited/merged derivatives without an explicit
exclusion/base-reconstruction record fail closed. Public output excludes the
declared private variants rather than claiming to reproduce them. No history rewrite.

Application delivery sanitizes or rejects derived payloads before copying them;
it must inspect actual tracked file contents and nested JSON, not file suffixes.
Staged-file checking and private/mod export share the provenance rules. Existing
public examples with unknown origin require explicit source records; the guard
is an enforceable boundary for recognized/declaratively tracked origins, not a
claim that arbitrary disguised copied pixels can be identified automatically.

## C4 continuation contract, fixed before C2 expansion

Retain legacy PC, 100-byte story window, menu selection and pending native/animation
state. Do not turn on authored events in an imported campaign in C2. C4 will add
engine-owned entry/return records: program ID, return label/PC, typed pending
operation, result destination, bounded call depth and RNG ownership. Compiler
version/program digest are pinned to saved continuations. Native action number
and building/context jointly select behavior. Save after purchase but before
recipient selection is an early bridge test; it must never charge twice.

## C3 spatial and presentation extension

The manifest optionally names `chi_spatial: chi-spatial.json`,
`chi_presentation: chi-presentation.json` and ordinary `graphics: graphics.json`.
These fields are accepted only with the imported-CHI dependency/startup contract.
They participate in the exact runtime fingerprint and source builds. A C2
project with neither new field keeps its previous resource behavior/identity.
Enabling or editing runtime content deliberately invalidates saves from its old
content revision; automatic migration is not part of this extension.

`btp-chi-spatial-v1` retains all 15 map slots and exact native header/padding
bytes. Display labels are sanitized independently; editing a label replaces its
slot's bytes. Cells reference stable tile IDs, whose graphic and native numeric
movement rule are separate. Custom artwork never supplies collision implicitly.
The renderer, movement, followers, combat placement and water queries use these
effective maps. Native mission gate/rubble/cache mutations retain priority.

The one world remains 1,024 × 1,024. Seed, coarse/flip tables, 17 join bindings,
jigsaw cells, land lookup and mini colours override the original generator's
inputs without changing its algorithm. Custom terrain handles remain 16-bit.
Town origins use 64-tile alignment. Moving the Citadel also moves its ruined
slot; native fixed-location callers rebase against immutable source-map origins.
Cached room coordinates retain their separate internal frame. Derived content
origins are reconstructed on load, not added to the serialized game state.

Bounds: 4,096 tile definitions; 1,024 jigsaws of 8 × 8; 15 maps, maximum 64 × 64;
16 door slots and eight NPC routes per map; at most 32 overlays per map. Maps
1/2/11/14 remain 64-square and map 15 remains 32 × 24. Citadel and starport keep
the adjoining-sector margins required by native battles. Town door slots 0–7
remain active for the original NPC protocol. New doors can select existing BLD
building IDs; recruit templates and authored event execution remain C4.
Updated's optional `services.broker` edits its existing virtual starport entrance
without altering the original MTP header. Original rejects that capability.

`btp-chi-presentation-v1` binds owned art to native tile/sprite/screen/font/film/
portrait resource indices. Native sheet/sprite patches use the specified named
display palette; map-owned art and full films/portraits retain RGBA. All 22 films
keep their original frame counts and 88-square dimensions; durations are native
retraces. Resource-aware save validation permits edited timing while retaining
native cutscene phase/count checks. Fonts are a 128-square atlas of 256 glyphs.
Audio references select verified programs 1–18, sound speed 25–400%, and title
music enabled/disabled. They do not import executable instructions or introduce
new sound synthesis programs.

The editor's adventure-shaped projection is an editing adapter only. Synthetic
building references never enable the authored event VM and are not written as
an adventure. Unsupported authored story/party/encounter edits fail validation.
GUI, CLI, Undo/Redo, source conversion/build, libraries and review/protection
operate on the same effective documents. Native rule values and presentation
tile patches participate in regional protection. Preview jobs use bounded native
decoder output: a 128-square world overview or a 2 MiB index grid, not a giant
full-resolution bitmap. Imported/derived artwork keeps origin metadata through
editing/cloning and dependency transfer; public-export rejection remains in force.

See the [schemas](../schemas/chi-spatial-v1.schema.json),
[presentation schema](../schemas/chi-presentation-v1.schema.json),
[usage](CHI_IMPORT.md) and [verification ledger](CHI_IMPORT_PROGRESS.md).

## C4.1 labelled BLD source extension

The optional manifest field `chi_scripts: chi-scripts.json` is accepted only
for imported-CHI native campaigns. `btp-chi-scripts-v1`, schema 1, contains
exactly 26 programs in native building order. Each declares its stable ID,
canonical resource/building identity, immutable baseline-payload SHA-256, entry
label and ordered typed records. Original records retain `origin` and
`original_size`; inserted records omit both. Every original byte range remains
represented exactly once. Unvisited ranges are preserved data, cannot change,
and cannot be reached by a branch or fall-through.

The C loader validates and compiles in two passes. Label references replace
absolute operands, while original arithmetic, dispatch and interpreter behavior
remain native. Source-enabled unedited files reproduce payload, encryption,
length word and padding exactly. `chi/*.BLD` files are immutable baselines;
compiled output is used in memory, never written over them. The source bytes,
`chi-bld-compiler-v1` contract tag and compiled payload hashes participate in
strict runtime identity. A project without this field retains its prior path.
Enabling it or editing runtime source requires new saves or the preserved older
project revision; no migration is implied.

Instruction starts and original instruction ends have distinct relocation maps.
Branch destinations resolve to starts; native service return boundaries resolve
to ends so newly inserted instructions execute after a suspended call returns.
Class, bank, training guards and save validators use these maps. During invasion
the training script retains ownership while the visible Citadel changes maps.
Derived maps are reconstructed from the exact source on load; serialized native
state and ordinary save formats are unchanged.

Compiler errors include program/instruction JSON paths, mapped through owned
source modules into the editor. GUI, CLI and authoring commands share validation,
revision/scoping/protection rules, atomic rollback, Undo, draft recovery and
Save/Play. Program scopes use `chi.programs/<program-id>`; command receipts
survive Undo. Original records cannot be deleted; only new records can be
removed, provided references still resolve. Human notes do not relax validation.

Bounds: 1–9,000 compiled bytes and 1–2,048 records per program; source JSON at
most 1 MiB/60,000 nodes; text operands at most 4,096 bytes, with eight active
native spans. Story operands address bytes 0–99. Menu destination counts match
the verified native selector. Native action/film combinations must occur in that
program's immutable baseline, and specialized class/training actions preserve
their semantic anchors. Unknown operations/fields, invalid operands/labels/data
targets, altered baseline ranges, incompatible contexts and exhausted budgets
fail visibly. Deterministic cycles without yields are rejected; conditional
loops retain the 256-instruction runtime budget. General calls/recursion,
authored-event bridging and automatic dialogue layout are outside C4.1.

Extracted source/data, dialogue and compiled output remain original-derived
private content under existing provenance/export rules. This does not make
native service inventories, mission definitions or recruitment templates
generally editable: those remain C4.2–C4.4. See [usage](BLD_AUTHORING.md),
[schema](../schemas/chi-scripts-v1.schema.json) and
[verification](TESTING.md#labelled-bld-authoring--2026-10-24).

## C4.2 native service content extension

`chi_services: chi-services.json` optionally declares `btp-chi-services-v1`,
schema 1, for an imported CHI campaign. There are 156 typed numeric parameters;
unknown keys, duplicate keys, booleans, bad ranges and unsupported spy odds fail
with parameter paths. Omitted keys use the effective immutable native defaults.
Optional `broker_stock` is a unique list of existing roster IDs; omission means
all stock and an empty list means none. It cannot grant an edition capability.
The file and service contract tag participate in strict content identity.

Cache-backed ammunition/refit/medical settings override the decoded in-memory
tables. Other parameters are resolved by the native transaction routines and
renderer through the same catalogue. Neither original cache bytes nor ordinary
game/save formats change. Built-in games and older imports without this field
keep their defaults. Native market parameters reach both cadet and later-world
clock callers; unsigned arithmetic and RNG draw ownership are retained.

BLD text and native dialogue overrides accept `{service:parameter.id}`, with
optional `:comma` formatting for text. Money operands accept one such reference
or their existing unsigned word. Expansion occurs before compilation/rendering;
source and expanded BLD text both retain the 4,096-byte budget. The configurable
positive arena prize stops at 32,767 because its native add-money operand is
signed. The compiler accepts stable `native.*` action names as aliases for the
same existing F5 numeric operation, with all context/anchor checks retained.

Enabling support binds only unchanged original price text and fee operands;
existing custom dialogue remains authoritative. Native repair fragments stay
in the existing campaign dialogue overrides. Price binding is explicit source,
not a renderer search/replace heuristic. Authors must keep remapped equipment
descriptions and custom literal prices consistent with their settings.

The native action catalogue records all 47 F5 operations and the 76 observed
building/action pairs, requirements, outputs, mutations, yields and errors.
E9 recruitment keeps its separate existing building/skill validation. This is
an inventory of the port's retained native contracts, not fresh DOS execution
proof of every pair. Services retain the original recipient, partial repair,
healing, spy replacement, theft and crew state machines. Class and prison save
validators receive current resources for configured prices/timers/attempts;
there are no new serialized continuation fields.

GUI, CLI, source builds, scoping, protection, receipts, history and recovery share
the same effective documents. Parameter scopes use
`chi.service_parameters/<parameter>` and stock uses `chi.broker_stock`. Enabling
also changes manifest/script/message bindings and therefore needs that broader
scope. Existing registered projects are not automatically upgraded. Preserve
their previous revision for old imported saves. All original-derived content
continues to follow private-import/provenance/export rules.

Native menu counts, refit recipes, character identities and party/bay capacities
remain bounded compatibility contracts. Mission opponents/spawns and yard combat
layouts remain C4.3; general authored-event calls remain C4.4. See
[service usage](CHI_SERVICE_AUTHORING.md) and
[schema](../schemas/chi-services-v1.schema.json).
